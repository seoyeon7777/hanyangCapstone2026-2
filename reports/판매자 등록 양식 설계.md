# 판매자 상품 등록 양식 설계 (앱 팀용)

## 왜 필요한가
상세 이미지·설명글에서 핏·기장 같은 정보를 읽는 방식은 한계가 확인됐다(시연 상품 36개에서 상품당 태그 평균 1.4개, 새 상품 20개 중 16개가 이미지 설명). 앱에서 상품 등록을 직접 받는다면 판매자가 항목을 고르게 해서 **주요 속성의 누락을 줄일 수 있다**. 글을 읽지 않으므로 키워드 추출 오탐은 줄어든다. 다만 판매자가 잘못 고르는 오류는 별도로 남는다.

## 적용 범위: 직접 등록 상품만
- 직접 등록 상품(`source="direct"`): 필수 항목 검증을 통과한 `attrs`가 우선한다. 필수 항목이 비면 오류다. 양식에서 비운 선택 항목(실루엣·허리·디테일·소재·종류)만 상품명·설명글에서 보충하고, 보충한 태그는 `text_added`에 따로 기록한다. 양식에 채운 값이 글과 충돌하면 양식이 이긴다. 핏·기장·혼용률과 섬유 태그는 글에서 보충하지 않는다. 판매자가 선택 항목을 비워도 글에서 일부 살아나므로, 비운 쪽이 손해라는 구조는 완화된다(태그가 없는 상품은 감점이 아니라 중립 점수).
- 팀 입력 상품(`source="manual"`): 팀이 외부 상품을 같은 양식으로 입력한 것. 검증과 태그 생성은 direct와 같고 출처만 다르다(보고서에서 판매자 입력과 팀 입력을 따로 센다). 입력 기준은 `상품 정보 입력 가이드.md`.
- 핏 표기는 `fit_stated`(slim / regular / over / unknown)로도 저장한다. 점수 태그는 slim·over만 만든다.
- 가져온 상품(무신사 등): 기존 글·이미지 추출을 쓴다. 이런 상품에 `attrs`가 오면 조용히 무시하지 않고 오류를 낸다.
- 필수 항목이 누락된 attrs는 허용하지 않는다. 선택 항목의 미입력 값만 텍스트로 보충한다.

## 항목 (정의 파일: `algorithm/data/attributes.json`, 앱 화면은 이 파일에서 만들 것)
카테고리(`category`)는 필수이고 top / outer / pants / skirt / dress 중 하나다.

| 항목 | 필수 | 적용 | 선택지 → 점수용 태그 |
|---|---|---|---|
| 핏 | O | 전체 | 슬림 → fit:slim / 레귤러 → 없음 / 오버(루즈) → fit:over |
| 기장(상의·아우터) | O | top, outer | 크롭 → len:crop / 기본 → 없음 / 롱 → len:long |
| 기장(팬츠) | O | pants | 쇼츠·무릎·종아리·발목·풀 길이 → 모두 태그 없음(근거가 없어 저장만) |
| 기장(스커트·원피스) | O | skirt, dress | 미니·미디 → 없음 / 맥시 → len:long |
| 실루엣 | | pants, skirt, dress | 와이드 → sil:wide / A라인 → sil:A / 일자 → sil:IH / 스키니 → sil:skinny / 해당 없음 |
| 허리 위치 | | pants, skirt | 하이웨이스트 → waist:high / 보통·로우라이즈 → 없음 |
| 디테일(복수) | | 전체 | 러플·프릴 → det:ruffle / 리본 → det:ribbon |
| 소재 종류(복수) | | 전체 | 니트·데님·가죽·퍼·시폰·벨벳·코듀로이·무스탕 → mat:* |
| 아이템 종류 | | 항목별 제한 | 테일러드 재킷(top·outer) → item:tailored_jacket / 타이트 스커트(skirt) → item:tight_skirt / 모헤어 니트(top·outer) → mat:mohair / 롱 카디건(top·outer) → len:long / 크롭 팬츠(pants) → len:crop |
| 혼용률 | O | 전체 | 섬유와 비율. 판매자 화면은 퍼센트(0 초과 100 이하)로 받고 앱이 `percent_to_share()`로 0~1로 바꿔 저장한다. 면·울·나일론·실크·린넨·캐시미어는 30% 이상일 때만 소재 태그. 폴리·레이온·아크릴·스판은 저장만 |

- 혼용률을 알 수 없거나 해당이 없으면(가죽·퍼 등) 수치 대신 `composition_status`로 "확인 불가" 또는 "해당 없음"을 고른다. 수치를 억지로 채우지 않는다. 수치와 상태를 함께 쓰면 오류다.
- 서버 검증(내부 비율 기준): 섬유별 0 초과 1 이하, 같은 섬유 중복 불가, 합계 1 ± 0.01, 알 수 없는 섬유 불가, 그 카테고리에 없는 항목·선택지 불가.
- 모순되는 선택은 서버가 오류로 거절한다(`attributes.json`의 `option_conflicts`). 현재 규칙: 롱 카디건은 상의 기장 "기본"·"크롭"과, 크롭 팬츠는 팬츠 기장 "풀 길이"·"쇼츠"와 함께 고를 수 없다. 앱 화면에서도 같은 조합을 선택하지 못하게 막을 것. 이 규칙 목록은 최소한이며, 다른 모순은 아직 검사하지 않는다.
- 같은 태그를 여러 항목에서 골라도(예: 기장 "롱"과 아이템 "롱 카디건") 한 번만 반영된다.

## 입력값 저장과 점수용 태그는 다르다
- `tag_from_attributes()`는 태그와 함께 검증된 입력값 전체(`attributes`)를 돌려준다. 앱은 이 값을 저장한다.
- "레귤러"나 "팬츠 발목 길이"처럼 점수용 태그가 없는 값도 저장된다. "레귤러를 골랐다"와 "핏을 모른다"는 다르다(후자는 필수 항목이라 오류).
- 따라서 **필수 입력은 주요 속성의 누락을 줄일 뿐, 점수용 태그가 몇 개 붙는지는 선택한 값과 혼용률에 달려 있다.** 예: 레귤러 핏, 기본 기장, 폴리에스터 100%를 고르면 점수용 태그는 0개다.

## 기장을 카테고리별로 나눈 이유
"롱 = 무릎 아래"는 상의에 쓸 수 없고, 팬츠·스커트도 기준이 다르다. 그래서 입력은 카테고리별 선택지로 나누어 저장하고, 기존 `len:crop`·`len:long` 태그로 연결하는 규칙만 카테고리별로 둔다.
- 상의·아우터: 크롭 → len:crop, 롱 → len:long.
- 스커트·원피스: 맥시 → len:long(기존 키워드 "맥시"·"롱스커트"와 같은 규칙).
- 팬츠 길이: 근거가 없어 연결하지 않는다. 논문이 든 "크롭 팬츠"는 아이템 종류에서 고를 때만 len:crop에 연결한다.
- 확인이 필요한 점: len:crop의 웨이브 +2는 논문의 아이템 "크롭 팬츠"와 얼루어의 "짧은 상의 + 하이웨이스트"라는 서로 다른 두 서술에서 왔다. 크롭 상의와 크롭 팬츠가 같은 체형 가중치를 받는 것이 타당한지는 검증된 바 없고, 지금은 같은 태그로 합쳐 둔 상태다.

## 이 양식으로 해결되는 것과 안 되는 것
- 해결: "옷에서 읽을 정보가 적다"를 줄인다(필수 속성 누락 감소, 키워드 추출 오탐 감소).
- 해결 안 됨: "점수에 쓸 항목이 적다". 양식 항목은 가중치표(출처 또는 설계 가정을 명시한 태그 26종)와 코디 밸런스 규칙에 있는 태그로 한정된다. 항목을 늘리려면 먼저 가중치(근거 또는 팀 가정)를 정해야 한다.
- 남는 위험: 판매자가 잘못 고르거나 대충 선택할 수 있다. 앱에서 기본 선택값을 두지 말고 선택 기준을 화면에 안내할 것. 판매자 입력의 신뢰도는 측정하지 않았다.

## 글 보충 규칙 (양식 우선)
- 보충은 "그 태그를 만드는 양식 항목이 모두 미입력인 선택 항목"일 때만 한다. 양식 정의(`attributes.json`)의 선택지-태그 대응에서 태그의 소유 항목을 구한다.
- 미입력과 "없다고 선택함"을 구분한다. 실루엣·종류·디테일·소재에는 "해당 없음", 허리에는 "보통"이 있어 이를 고르면 입력된 것으로 본다(보충하지 않는다). 디테일·소재는 처음에 "해당 없음" 선택지가 없어 구분이 안 되던 것을 추가했다. 다중 선택에서 "해당 없음"은 다른 선택지와 함께 고를 수 없다.
- 필수 항목이 만드는 태그는 보충하지 않는다. 예를 들어 설명의 "롱 카디건"이 만드는 `len:long`(기장은 필수 입력이 이긴다), 설명의 "면 100%"가 만드는 섬유 태그(혼용률은 필수 입력이 이긴다)는 붙이지 않는다. 종류에서 "해당 없음"을 골랐다면 "모헤어 니트"(종류 항목의 태그)도 붙이지 않는다.
- 양식에 없는 태그(목선 등)는 보충하지 않는다. 보충한 태그는 `text_added`에 따로 기록한다.

## 리뷰 일치도 (실험 기능, 기본은 표시만)
- 구매자가 리뷰에서 "상품이 등록 정보와 같았나요?"에 답하고, `review = {"n", "mismatch"}`로 넘기면 `review_agreement = (n - mismatch + k0) / (n + k0)`를 계산해 출력에 싣는다(k0 = 3). 리뷰가 없으면 1.0이다(등록 정보를 그대로 믿는 설계).
- 이 값은 "등록 정보의 정확도"가 아니라 "리뷰 응답에 따른 일치도"다. 구매 사이즈·체형에 따라 같은 상품도 다르게 느낄 수 있어 등록 오류를 확정하지 못한다.
- 점수 반영은 `review_mode`로 켠다. `off`(기본): 점수에 반영하지 않는다. `both`: 점수를 중립 쪽으로 당긴다. `positive_only`: 중립보다 높은 점수만 당긴다.
- `both`에서는 낮은 점수도 중립 쪽으로 올라오므로, 일치도가 낮은 상품이 일치도 높은 같은 점수대 상품보다 더 위로 올라올 수 있다(`tools/review_demo.py`로 확인). `positive_only`는 이를 막는다. 어느 쪽도 근거는 없다.
- 근거 없는 부분: k0=3, 선형 보정, 몇 건부터 의미 있는지. 리뷰어 체형이 달라서 생긴 불일치와 등록 오류를 구분하지 못한다.
- 하지 않은 것: 방향(작게/크게 나온다)을 읽어 핏 태그를 바꾸는 것, 글 리뷰 분석.
