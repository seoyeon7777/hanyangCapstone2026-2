# 로직 완성도 점검 (A · B · C)

목적: 가중치·태그 신뢰도는 JSON 교체로 해결되므로 제외하고, **로직이 설계대로 움직이는지**와 **적용 시 예상 못한 문제**만 본다.
방법: 각 파트 코드를 직접 실행해 재현. 아래 분류는 ① 재현된 결함 ② 설계상 위험(측정) ③ 이상 없음 확인.

## A (체형 분류)

### ① 재현된 결함
- measurements에 리스트 등을 넣으면 `InputError`가 아니라 AttributeError.
- bool 답(True/False)이 정수로 받아들여짐.

### ② 설계상 위험(측정)
- q4 선택지 1번이 S1·W1을 동시에 올려, 다른 문항 고정 시 **비단조(점수가 올라야 하는데 내려가는) 사례 307/30,618**.
- 아바타 비율 지표가 W쪽으로 치우침, THRESHOLDS 구간이 좁음, 표본이 작음(이전 점검 결과).

### ③ 이상 없음
2,187개 답변 조합에서 출력 불변식 성립(비율 합 1, primary/is_mixed 일관), 결정적, 치수 단위 배율에 불변.

## C (추천 · 홈 피드)

### ① 재현된 결함
| # | 내용 | 확인 |
|---|---|---|
| C1 | **오늘의 추천이 10개 미만으로 끝남**: 대표 태그 ≤3 규칙 때문에, 같은 대표 태그 상품만 남으면 중단. 슬림+면 상품 60개 카탈로그 → 3개만 반환(스크롤은 60개 전부) | 재현 |
| C2 | 스크롤 페이지 중 대표 태그 3개 초과 페이지가 있음 (588개 카탈로그, 58페이지 중 2페이지) — 설계 규칙이 홈 상단에만 보장되고 스크롤에선 일부 깨짐 | 재현 |
| C3 | **원피스 섹션이 항상 비어 있음** (B 쪽 카테고리에 원피스가 없고 outfits도 상의×하의만) | 재현 |
| C4 | NaN/inf 비율이 400이 아니라 200으로 통과하고 응답 body 점수가 전부 0.0, bool 비율(True→1.0)도 통과 | 재현 |
| C5 | 취향(pref)이 상품 단위가 아니라 **태그 단위**이고 포화(±1)가 빨라, 같은 상품 click 20번이면 구매 1회 효과를 넘어 1.0에 도달. like 10번이면 포화, 이후 return 10번이면 −1 | 재현 |
| C6 | 재진단 안내가 **같은 옷 하나를 10번 좋아요**해도 발동 (상품 수가 아니라 반응 수로 셈) | 재현 |

### ② 설계상 위험(측정)
- 혼합형일수록 body 점수 범위가 좁아짐: S_N 0.319~0.598, N_S 0.362~0.561 vs 단일형 pure_S 0.167~0.778. 최종 점수에서 body 0.60이 취향·트렌드(0.40)에 쉽게 묻힐 수 있음.
- 체형 최하 상품도 취향이 만점이면 최종 0.521로, 체형 최상(선호 0) 0.69와 차이가 크지 않음 — 취향이 쌓이면 체형 기반 추천이 약해짐(되먹임).
- 상품 목록이 `items.json` 고정 30개이고 `seasons`·`popularity` 필드를 요구함 → B의 등록 상품과 연결할 때 필드 불일치.

### ③ 이상 없음
모든 API 퍼징(깨진 JSON, 문자열·리스트 비율, 음수, 0, 거대 page, 긴 user_id)에서 500 없이 400/200. feed_order는 전 상품을 중복 없이 노출하고 결정적. 같은 category 연속 ≤2 규칙은 모든 프로필에서 준수. 반응 5,000개 로딩도 즉시.

## 정리: 먼저 고칠 것 (내 코드 B)
1. 프로필 검증: 비율 유한성(NaN/inf), primary·is_mixed 일관성 → 400
2. 등록 검증: item_id/name/desc/tags 타입, category 필수 → 400
3. 자동 item_id 충돌, 중복 id 처리
4. `_STYLING_TAIL` 공백 이차 시간 수정 + 요청 크기 제한
5. 코디 후보 수(top_k) 확대 또는 전수 비교

A·C에게 전달할 것: A(리스트/bool 입력, q4 1번 문항), C(C1 10개 미만, C2 스크롤 규칙, C3 원피스, C4 NaN 검증, C5 포화·연타, C6 재진단 셈법).

한계: C 파트는 B가 만든 588개 격자 카탈로그를 C 형식으로 변환해 실행했고(대표 태그가 실제 상품보다 균일할 수 있음), seasons/popularity는 무작위로 채움.


## 후속: B 수정 결과 (10/16)
B1~B8 모두 수정, 회귀 시험 `tests/test_robustness.py` 추가 (전체 233개 통과).
- B1·B2: `normalize_profile`이 NaN/inf를 거부하고, primary가 비율 최대 유형이 아니면 거부 (동률은 허용). is_mixed 기준(gap<0.10)은 A의 설계라 B에서 재계산하지 않음.
- B3·B5: `matching.validate_item` 추가 — item_id(문자열/정수), category(알려진 값), name/desc 문자열, desc 5000자 이하, tags 문자열 목록. `recommend`와 서버 등록·추천에서 사용 → 400.
- B4: `recommend`가 중복 item_id를 거부.
- B6: 자동 item_id를 카운터로 바꾸고 이미 쓰인 id는 건너뜀.
- B7: `_STYLING_TAIL`의 공백 반복을 최대 3칸으로 제한, `_clean_desc`가 5000자까지만 읽음 (다른 정규식도 긴 반복 문자열에서 제곱 시간이라 길이 상한으로 막음), 서버 요청 1MB 제한(413).
- B8: `outfit_top_k` 20 → 50 (S_N 최고 코디 0.5629 확인, 전수 탐색 대비 0.02초).
- 추가로 발견·수정한 500: `composition_percent`/`composition`의 모양이 틀릴 때(객체·문자열·정수 항목) AttributeError → 400. 본문이 JSON 객체가 아닐 때도 400.
- 남은 한계: 설명 5000자 상한은 임의값(실제 샘플 최대 131자). 코디 후보 수 50도 설계 값이라 상품이 수천 개가 되면 재검토 필요.
