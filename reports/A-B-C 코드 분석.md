# A·B·C 코드 분석 (2026-10-16)

읽은 코드: A = `feature/jihyun`·`feature/seoyeon-a-fix`의 `body_profile.py`·`evaluate.py`·`sample.csv`, B = `feature/yeonoh`(태깅 분리본), C = `feature/seoyeon-db`의 `app.py`·`recommend/`(가장 많이 진행된 C 브랜치).
숫자는 코드를 직접 돌려 얻은 값이다. 추정한 부분은 "추정"이라고 적었다.

## 1. 한눈에 보는 연결 구조
```
A classify(answers, measurements) -> {ratios, primary, secondary, confidence, is_mixed}
   │  (C의 feed_api가 호출, 또는 앱이 profile로 전달)
   ▼
C feed.py: 최종 = 0.60 체형 + 0.25 취향 + 0.15 트렌드
   │  체형 점수  <- B match_item(...)["body_fit"]       (recommend/matching_b.py 어댑터)
   │  코디 보정  <- B balance_adjustment(...)
   │  추천 이유  <- B reasons
   ▼
상품: C의 recommend/data/items.json (가짜 30개)   ← B에 등록한 상품과 연결되어 있지 않다
```
C가 실제로 쓰는 B 함수는 `load_rules`, `match_item`, `balance_adjustment` 셋뿐이다. B의 `recommend`, `rank_items`(blend·quota), `recommend_outfits`, `/api/recommend`는 피드에서 쓰이지 않는다.

## 2. A (체형 분류)

### 설계
- 설문 7문항(가중치 1.5/1.0)을 타입별 점수로 바꾸고, 타입별 최고점(S 15 / W 14 / N 13.5)으로 나눈 뒤 합이 1인 비율로 만든다 (a-fix에서 추가).
- 아바타 치수 5개를 비율 지표 3개(상체÷다리, 어깨÷키, 팔÷키)로 바꾸고 기준 구간 안의 위치로 점수를 낸다.
- 설문 0.6 + 아바타 0.4로 합치고, 1·2위 차이가 0.10 미만이면 `is_mixed`.
- 입력 검증(`InputError`)이 꼼꼼하다 (범위, 누락, 상체+다리 ≥ 키 등).

### 직접 돌린 결과 (`sample.csv` 33행, 입력 오류 3행 제외)
| | 튜닝 21명 | 테스트 9명 |
|---|---|---|
| 합산 (현재) | 20 | 9 |
| 설문만 | 17 | 8 |
| 아바타만 | 11 | 6 |

### 부족한 점
1. **표본이 작다.** 타입별 8명 + 3명이고 정답 라벨을 누가 어떻게 붙였는지 코드에서는 알 수 없다. 테스트 9/9여도 95% 신뢰구간 하한은 약 66%다. 이 수치는 "이 30명에서 맞았다"이지 정확도 검증이 아니다.
2. **아바타 점수가 W 쪽으로 기운다.** 아바타 지표의 타입별 최고점이 S 1.65 / W 2.25 / N 1.1인데 설문과 달리 최고점으로 나누지 않고 비율을 만든다. 지표 위치를 무작위로 뽑으면 아바타 1위가 W 63% / S 34% / N 3%다. 샘플에서도 정답이 N인 10명 중 아바타 단독으로 N을 맞힌 사람은 1명이다. `CLAUDE.md`는 "타입별 최대점으로 나눈다(S 7 / W 9 / N 6)"고 적었지만 코드는 설문에만 적용돼 있어 문서와 코드가 다르다.
   - 최고점으로 나눠 보면 아바타 단독은 11→12(튜닝), 6→8(테스트)로 좋아지지만 합산은 20→18(튜닝), 9→9(테스트)다. 기준 구간과 0.6/0.4를 지금 설정으로 맞춘 것이라 다시 튜닝해야 비교할 수 있다.
3. **기준 구간이 아주 좁다.** 어깨÷키는 0.1923~0.1982(키 165cm면 어깨너비 약 1cm 차이)다. 치수를 ±1cm 흔들면 아바타 단독 판정은 18% 바뀐다. 합산 판정은 3%만 바뀌므로 설문이 안정시켜 주고 있다. 카메라 치수 오차가 1cm보다 크면 아바타 40%는 사실상 잡음이다 (추정: 카메라 오차는 확인하지 못했다).
4. 함수 하나 + 시연 출력 구조이고 테스트 코드는 없다(`evaluate.py`만 있다). `confidence`는 이름과 달리 1·2위 차이다.

### B에 주는 의미
출력 모양은 B의 profile과 같아서 연결에는 문제가 없다. 다만 W가 과대 판정될 수 있어서 B의 W 가중치 근거가 약한 점과 겹친다.

## 3. C (추천·홈 피드)

### 설계
- 최종 점수 = 0.60 체형(B) + 0.25 취향 + 0.15 트렌드(계절 0.5 + 인기 0.5). 동점은 id 순이라 결과가 항상 같다.
- 정렬 뒤 다양성 규칙(같은 category 연속 2개, 같은 대표 태그 3개)을 적용하고, 홈 섹션(오늘의 추천·카테고리·코디)과 무한 스크롤을 만든다.
- 취향은 사용자 반응(클릭·찜·구매·반품)을 태그 단위로 누적한다. 최근 긍정 반응이 진단과 어긋나면 재진단을 안내한다.
- 토글 OFF는 체형 없이 인기·취향·계절로 추천한다.
- SQLite로 사용자·반응을 저장하고(취향은 매번 반응 기록에서 다시 계산), Flask Blueprint와 통합 서버 `app.py`가 있다. 오류는 모두 JSON이다.
- 설정은 `rec_config.py` 한 곳에 모았고 테스트도 많다.

### 부족한 점
1. **상품이 가짜 30개다.** `items.json`을 import할 때 한 번 읽는다. B에 `/api/items`로 상품을 등록하고 `/api/feed`를 불러 확인했는데 피드에 나오지 않았다.
2. **혼합형에서 체형이 거의 영향을 못 준다.** 30개 상품 기준으로 최종 점수에 체형이 주는 폭은 순수형 S 0.37, W 0.30, N 0.35이고 트렌드가 주는 폭은 0.094다. 혼합형은 S+N 0.17, S+W 0.21, W+N **0.10**이라 W+N에서는 체형 차이가 계절·인기 차이와 같아진다. 상위 10개도 혼합형(S+N)과 단일형(S)이 6개만 겹친다. 이유는 B의 혼합형 점수가 비율로 섞여 0.4~0.55로 모이기 때문이다.
3. **혼합형이어도 1위 유형만 본다.** `good_tags`·`avoid_tags`, 대표 태그 제한, 재진단 판단이 모두 `primary`의 가중치만 쓴다. S 0.41 / N 0.38 사용자에게 N에 좋은 태그(`fit:over` 등)는 어울림 태그에 나오지 않는다. 코디 보정(`balance_adjustment`)만 비율을 쓴다.
4. **B의 순위·코디 로직과 중복된다.** 코디는 상의×하의만 있고 아우터·원피스는 코디에 들어가지 않는다 (B의 `recommend_outfits`는 아우터를 포함한다). B의 `mixed_strategy`도 쓰지 않는다.
5. **옛 태그 체계 잔재.** `rec_config.py`의 `STYLE_TAGS`·`TAG_GOOD` 등과 `fake_matching.py`, `items_fake.json`은 지금 `test_feed.py`만 쓴다.
6. **테스트가 함께 돌리면 깨진다.** `test_feed.py`가 import할 때 `feed.match_score`를 가짜 매칭으로 덮어써서, `pytest recommend`로 전부 돌리면 6개가 실패한다(`test_api`·`test_integration` 일부). 파일별로 돌리면 api 20 / feed 38 / integration 8 / store 5 모두 통과한다.
7. 취향이 체형 점수와 같은 태그를 쓴다. 슬림핏을 누르면 체형(슬림 가산)과 취향(슬림 가산)이 겹쳐 반영된다. 반응 감쇠도 없다.
8. `category`가 `bottom` 하나인데 B는 `pants`·`skirt`·`dress`를 쓴다. 변환이 필요하다.

## 4. B (내 코드)

### 설계
- 규칙은 `data/*.json`, 태깅(`tagging.py`: 양식 우선 + 글 보충), 점수·이유·코디(`matching.py`), 등록·검증 API(`server.py`).
- 테스트 188개, 가중치 근거 문서, 시험 보고서.

### 부족한 점
1. **C와 이어지는 부분이 작다.** C가 쓰는 건 `match_item`·`balance_adjustment`·`load_rules`뿐이다. 나머지(`recommend`, `rank_items`, `/api/recommend`)는 평가용으로 남아 있다.
2. **등록한 상품이 피드로 가지 않는다.** B 저장소는 서버 메모리라 끄면 사라지고, C 피드는 별도 가짜 파일을 읽는다. 상품에 `seasons`·`popularity`도 없다.
3. **혼합형 점수 폭이 좁다** (C 2번의 원인). N 쪽 쏠림과 W·S 근거 부족 문제도 남아 있다 (`가중치 쏠림 점검.md`, `가중치 추가 근거 조사.md`).
4. `avoid_mode`(penalty/exclude)와 `mixed_strategy` 결정이 팀 합의 없이 남아 있다. C의 재진단은 `avoid_tags`에 의존한다.

## 5. B를 어떻게 할지 (우선순위)
1. **상품 연결.** 팀이 정해야 할 것: 상품 저장소를 어디에 둘지 (C의 SQLite에 `items` 표를 추가하는 안이 현재 구조에 가장 가깝다). B가 할 일: 등록 양식에 `seasons`(복수 선택)를 넣고 `popularity`는 기본값으로 둔다 → C 상품 모양으로 바꾸는 `to_feed_item()` 추가 (`pants`·`skirt` → `bottom` 변환 포함). 등록 때 이미 태그를 저장하므로 C는 저장된 태그만 읽으면 된다.
2. **혼합형 지원 함수 추가.** `good_tags`·`avoid_tags`를 비율 가중치로 계산해 주는 함수를 B가 제공하고 C의 어댑터가 이를 쓰게 한다. 지금은 C가 `primary`만으로 계산한다.
3. **혼합형 점수 폭.** C와 합의: B가 점수 눈금을 늘려서 줄지, C가 체형 비중을 혼합형에서 키울지, 상품 집합 안에서 상대 점수로 바꿀지. 어느 쪽이든 위 30개 상품과 A 출력 2,187가지로 바꾸기 전후를 같이 측정한다.
4. **API 범위 정리.** 서비스에서 쓰는 것(등록·검증·태그·`match_item`·`balance_adjustment`)과 평가용(`recommend`·`rank_items`·quota)을 문서에서 구분한다. 코드를 지울 필요는 없다.
5. **결정할 것:** 가중치 후보 3개(W 와이드 0, W 슬림 +1, S 울 +1) 반영 여부, `avoid_mode`, `mixed_strategy`.

## 6. 다른 파트에 전달할 것
- **A:** 아바타 점수의 타입별 최고점 보정, 문서와 코드 불일치, 라벨 출처와 표본 확대.
- **C:** 상품 연결, 혼합형에서 체형 영향이 작은 점, `test_feed.py`의 전역 덮어쓰기, 코디에 아우터 미포함.
